# pass-radar v3 Debug Capture and Current-Firmware Hardware Test Plan

Chinese version: `pass-radar-v3-debug-capture-and-current-hardware-test-plan.zh_CN.md`

Date: 2026-09-20
Firmware scope: the current production image generated by `./tools/validate.sh --firmware`
Status: basic hardware regression is complete; Debug Capture MVP is implemented and awaits hardware validation.

## 1. Decision and scope

Hardware testing is appropriate for basic function and stability, but not yet for parameter tuning. The simulator verifies only production boot and first-frame rendering. FTM, RSSI, ESP-NOW, BLE, CSI, token behavior, buttons, and direction accuracy require hardware.

The current hardware-test goal is to confirm that the production firmware boots, discovers a peer, runs FTM when possible, falls back safely, enters sweep, renders the result, and remains stable. Manual observations must not yet be used to tune distance, P25, RSSI, token, direction, or obstruction parameters.

## 2. Current implementation baseline

The current firmware includes:

- FTM calibration state, recent-session history, P25 output, and recent success-rate tracking;
- `FTM_GRANT`, `FTM_BUSY`, and `FTM_CALIB` protocol fields with token watchdog logic;
- 50 ms tracking updates, 25 ms sweep updates, six-second sweep target, and up to 256 RSSI samples;
- RSSI fallback when FTM is unavailable or a session fails;
- Debug-page FTM status, success-rate, history, and split BLE stack/peer diagnostics;
- one production firmware path for hardware and simulator;
- RTC and NVS diagnostic breadcrumbs;
- USB Serial/JTAG logging with an auto-reconnecting host monitor.

The following remain unproven until controlled capture data exists:

- distance accuracy and calibration quality;
- P25, IQR, and history-window tuning;
- token fairness and long-term alternation;
- sweep sample completeness and direction accuracy;
- BLE thresholds and obstruction thresholds.

## 3. Debug Capture design

Debug Capture is a diagnostic function. It must not change normal tracking or sweep behavior.

### 3.1 Entry and target label

Suggested interface:

```text
DEBUG CAPTURE
TARGET: 3m
UP/DOWN SELECT
OK START
```

The first version should use preset labels:

```text
1m / 3m / 5m / 8m / 10m / 15m / 20m / 30m
```

The display must say `TARGET`, not measured truth. A tape-measured distance is required for accuracy work. An approximate value is only a grouping label and must not be treated as ground truth.

### 3.2 Fixed capture state machine

```text
SELECT_DISTANCE -> COUNTDOWN 3s -> SETTLE 5s -> CAPTURE 30s
                 -> SUMMARY -> SAVE / DISCARD / NEXT
```

Countdown data is discarded. Settle data is excluded from the formal window. Capture uses a fixed duration and fixed fields. A reboot or write failure invalidates the run instead of silently joining two runs.

### 3.3 Raw fields

At minimum, each observation should contain:

```text
test_id
firmware_version
boot_sequence
target_distance_label_m
elapsed_ms
local_rssi_dbm
peer_rssi_dbm
peer_alive
espnow_rx_count
espnow_drop_count
ftm_session_id
ftm_status
ftm_raw_m
ftm_session_median_m
ftm_p25_m
ftm_iqr_m
ftm_history_spread_m
ftm_calibrated
ftm_token_role
ftm_grant
ftm_busy
ftm_calib
csi_frame_count
csi_selectivity_db
env_level
obstruction_class
channel
sweep_id
sweep_sample_count
reset_reason
```

Records should remain in RAM during capture and be written in one batch. Per-sample NVS writes are not recommended. Export should use CSV or JSONL over USB, and erase should be allowed only after a successful export.

## 4. Hardware test tasks

`S` means one person can perform the test. `O2` means a second person is useful but optional. An O2 test must be recorded as `NOT RUN (O2 optional)` when no second tester is available.

### H-00: pre-test check — S

Use the same production image on both cards. Confirm that the selected meta-pass slot launches the image, record the slot, image size, and installation time, retain NVS unless explicitly testing a clean state, and prepare a tape measure and USB log. The Capture test does not require slot2 specifically; any known-good bootable slot is acceptable.

### H-01: single-card boot stability — S

Run one card for at least 60 seconds without input. Pass requires STATUS, no reboot, no white screen, no exit, and a safe waiting or out-of-range state without a peer.

### H-02: second-card join — S

Run card A, start card B, place them about 3 m apart, and observe for 60 seconds. Pass requires both cards to remain alive and at least one side to show a stable peer or `2way` state without white screen, exit, or reboot.

### H-03: RSSI fallback — S

Run both cards 3–5 m apart for 60 seconds. Do not judge accuracy. Pass requires a failed FTM session to leave an explicit RSSI fallback or an explicit no-link state, with no hang or reboot. `1way[--]` alone proves only that a peer is unavailable; it does not prove RSSI fallback.

### H-04: Debug page and status — S

Enter Debug using the current UP double-click path. Confirm no crash or glyph corruption. `FTM WAIT` means a session is pending; a later session must automatically replace it with `FTM ok` or `FTM fail`. A permanent `FTM --` state is a failure.

### H-05: FTM observation — S

With both cards fixed about 3 m apart, observe for 60 seconds. One session is the sequence `Starting FTM session` followed by `FTM session ends ...`; `radar_ftm: FTM ok` means the application accepted the report. This task checks existence and recovery, not accuracy.

### H-06: token observation — S, O2 recommended

Run both cards for two minutes and collect both logs when possible. The new diagnostic output must show `FTM_TOKEN role=... grant=... busy=... calib=...`. RSSI changes alone are not evidence of token alternation. No simultaneous-initiation crash is necessary but not sufficient for a token pass.

### H-07: enter sweep — S

Press OK once from STATUS. Pass requires entry into SWEEPING, visible animation, completion without interruption, and no reboot or white screen.

### H-08: sweep timing and sample smoke check — S

Use USB logging and record `SWEEP_START`, `SWEEP_DONE elapsed_ms=...`, and `SWEEP_SAMPLES count=...`. The target is approximately 6000 ms. A manually estimated duration or an unreported sample count is not sufficient for parameter acceptance.

### H-09: result page — S

Pass requires a result page, return to STATUS, readable characters, and no crash. The result page must also retain the radar panel, draw a target point from the result angle, and place direction, angle spread, distance, and confidence text below the panel. Direction accuracy is not judged here.

### H-10: short soak — S

Run both cards for ten minutes and perform three sweeps with at least 30 seconds between them. Pass requires no reboot, white screen, exit, hang, or corruption, and repeatable STATUS/SWEEPING transitions.

### H-11: meta-pass launcher compatibility — S

Launch pass-radar from the selected meta-pass slot and verify the documented OK LONG2 return path. Do not use UP long-press for this test. Pass requires normal launch and return without corruption or reboot loops. This launcher-compatibility check is separate from Capture and does not require slot2.

## 6. Implemented diagnostic and visualization changes

The current development image contains:

- static FTM report buffers to prevent `sys_evt` stack exhaustion;
- `FTM WAIT` rather than a sticky ambiguous `FTM --` state;
- `FTM_TOKEN` role/grant/busy/calib change logs;
- `SWEEP_START`, `SWEEP_DONE elapsed_ms`, and `SWEEP_SAMPLES count` logs;
- a RESULT radar panel recreated after page teardown;
- a result target point based on the measured sweep angle;
- result direction, angle spread, distance, and confidence text below the panel.

These changes passed repository checks, host tests, firmware build, protected-layout validation, and simulator boot/first-frame validation. They still require hardware retesting.

## 7. Debug BLE status semantics

The Debug page reports two independent BLE states:

- `BLE S:OK` means the local BLE/NimBLE controller, advertising, and scanning procedures initialized successfully; `BLE S:NO` means the optional BLE subsystem is unavailable.
- `P:YES` means a matching peer sentinel was received within the 10-second liveness window; `P:NO` means no current matching peer advertisement is available.
- `age=...ms` is the age of the last matching peer advertisement. It explains why `P:NO` can occur even while the local BLE stack remains healthy.

The compact display format is:

```text
BLE S:OK P:YES r-68 age2s
BLE S:OK P:NO  r-68 age12s
BLE S:NO  P:NO  r-- age--
```

`r` is the last matching peer RSSI, even after the peer has left the 10-second live window. `age` is the age in seconds of that last matching advertisement. A `BLE S:OK P:NO` display is therefore normal during scan gaps, FTM/sweep coexistence pauses, or when the peer is not advertising. It is not evidence that BLE initialization failed.

## 8. Crash diagnosis and USB monitoring

The production image uses ESP32-C3 USB Serial/JTAG. The host monitor reconnects after USB re-enumeration:

```bash
cd /Users/alex/ai-passport/pass-radar
python3 tools/monitor-usb.py --output /tmp/pass-radar-usb-monitor.log
```

The monitor does not toggle DTR/RTS or intentionally reset the board. Start it before powering or resetting the card. Preserve the log after a failure and inspect `previous NVS` and `previous RTC breadcrumb` on the next boot.

RTC breadcrumbs avoid relying on Flash writes during panic. A complete brownout backtrace is still not guaranteed because power loss can remove both CPU execution time and USB transport.

## 9. Current USB evidence and diagnostic interpretation

The latest USB monitor log must not be summarized as “FTM always fails.” It contains both outcomes: 228 session starts, 222 session reports, 80 `FTM ok` records, and 12 explicit failure status records. The main failure codes observed were status 5 (no measurements from the responder), status 6, and status 3.

The Debug page reports the freshness of the current FTM snapshot, not the complete historical result set. A successful snapshot older than the five-second validity window is displayed as unavailable, while `radar_ftm_last_status` reports the most recent failure. These are different facts and must not be conflated.

The responder role is not itself an error. In v3, a responder may initiate when it receives the FTM grant token. `FTM_TOKEN role=RESPONDER grant=1` is therefore evidence that the token was granted, not evidence of an invalid role.

The USB diagnostic stream now includes:

```text
BLE peer matched rssi=...
BLE_STATE ready=1 peer=1 rssi=... age_ms=... scan=1 adv=1
FTM_SESSION start=... role=... probe=... rssi=... channel=...
FTM_SESSION end=... result=OK ...
FTM_SESSION end=... result=FAIL status=...
FTM_SESSION end=... result=TIMEOUT status=...
```

`BLE S:OK P:NO` on the screen should correspond to `BLE_STATE ready=1 peer=0`; this means the local BLE stack is healthy but no matching sentinel is currently inside the ten-second liveness window. `expected=1` means an ESP-NOW-validated identity is bound. `BLE candidate rejected` identifies a scan candidate that was rejected because it was not the bound peer. `FTM WAIT`, `FTM fail`, and `FTM ok` should be interpreted together with session number, busy state, snapshot age, and success rate.

The latest hardware check confirmed that the BLE fields visible on the Debug page match the corresponding USB log fields (`ready`, `peer`, RSSI, and age). BLE diagnostic observability is therefore accepted. This does not yet establish BLE range or obstruction performance; those still require controlled capture data.

## 10. Implemented Debug Capture MVP

The current production image implements the first static-distance capture loop:

```text
Debug target selection -> COUNTDOWN 3s -> SETTLE 5s -> CAPTURE 30s
                       -> SUMMARY -> batch Flash save -> USB CSV output
```

UP/DOWN on the Debug page selects one of the preset target labels, and OK starts the run. The target is a label only; it is not treated as measured truth. The capture page reports phase, elapsed time, record count, validity, and `SAVED CSV` after a successful batch write. OK returns to Debug; OK during an active run aborts it and marks the run invalid. DOWN long-press on Debug re-exports the last valid Flash record without erasing it.

The MVP stores up to 128 observations in RAM at a 250 ms cadence. At completion it erases and rewrites the dedicated `radar_capture` data partition in one batch, validates the record payload with CRC32, and emits a stable CSV header followed by `CAPTURE_CSV` rows over USB. A write failure marks the run invalid. The MVP exports immediately after save and supports repeated export of the last valid Flash record through the Debug-page DOWN long-press. It intentionally has no erase action yet, so raw evidence cannot be deleted accidentally.

The MVP fields are the available raw RSSI, peer liveness, FTM status/distance/spread/session count, BLE state/RSSI/age, CSI frame count, and environment level. The saved header and `CAPTURE_META` line now also include firmware version, capture ID, boot sequence, reset reason, target label, record count, and CRC32. Token fields, obstruction class, channel, and persistent re-export/erase controls remain to be added before using the output for final parameter tuning.

## 11. Build environment and exact firmware command

Build the production image from the repository root on macOS/Linux with ESP-IDF 5.5.3 and the existing uv-managed Python environment. The build timeout for this command is 15 minutes; it produces the only firmware image used by meta-pass, hardware, and passport-sim.

```bash
cd /Users/alex/ai-passport/pass-radar

export IDF_PATH=/Users/alex/esp/esp-idf-v5.5.3
export IDF_PYTHON_ENV_PATH="$HOME/.espressif/python_env/idf5.5_py3.10_env"
export PATH="$IDF_PYTHON_ENV_PATH/bin:$PATH"
source "$IDF_PATH/export.sh"

idf.py --version                         # must report ESP-IDF v5.5.3
./tools/validate.sh --firmware           # 15-minute build gate
IMAGE="$(ls -t build/pass-radar_*.bin | head -1)"
printf 'Firmware: %s\n' "$IMAGE"
shasum -a 256 "$IMAGE"
```

Use the newest versioned file under `build/`, represented by `$IMAGE` above. The final path will look like:

```text
build/pass-radar_v0.1-<commit>.bin
```

Do not flash or give to passport-sim the intermediate files `build/pass-radar.bin` or `build/pass-radar-full.bin`. Do not build a simulator-specific firmware. If the local ESP-IDF path differs, replace only `IDF_PATH`; keep the required version at 5.5.3. The command must be run again after any source change; an older image must not be used to evaluate the current commit.

## 12. Capture MVP hardware validation procedure

### 12.1 Required environment

The first validation should use one operator and two cards. A second operator is optional and must not be required for the basic acceptance run.

Required:

- two cards running the same newly built production image from a known-good meta-pass boot slot; slot2 is optional;
- the selected slot is recorded for each card, and the image version is confirmed at boot;

- stable power for both cards; avoid changing USB hubs, cables, or power sources during capture;
- a data-capable USB cable and access to at least one card's USB Serial/JTAG port;
- a tape measure and a quiet, fixed test location;
- a measured target distance, with both cards stationary and their intended front directions marked;
- no browser WebSerial page, `idf.py monitor`, or other serial client open on the monitored port.

For the first run, use one measured distance such as 3 m. The UI label must match the measured setup, but the label remains metadata rather than truth until the physical measurement is recorded with the log.

### 12.2 Flash and start logging

Keep the existing working slot and its fallback firmware unchanged. Install the versioned production image into the selected bootable slot on both cards; slot0 is acceptable if it is the current known-good launch slot. Do not erase NVS for this validation: this preserves device identity, diagnostic breadcrumbs, calibration/history, and peer state. NVS erasure is not required by Capture, but a clean-NVS experiment must be a separate, explicitly recorded test. Verify the displayed/app-log version matches the image selected from `build/`.

If the current layout is `slot0=pass-radar`, `slot1=occupied`, `slot2=empty`, it is valid for Capture provided slot0 boots the newly built image. The occupied slot1 and empty slot2 do not affect the Capture state machine, BLE, FTM, RSSI, or the `radar_capture` data partition. The trade-off is only rollback/launcher safety: do not overwrite slot1, and verify the meta-pass return path before relying on it.

Start the reconnecting monitor before powering or restarting the first card:

```bash
cd /Users/alex/ai-passport/pass-radar
rm -f /tmp/pass-radar-usb-monitor.log
python3 tools/monitor-usb.py \\
  --output /tmp/pass-radar-usb-monitor.log
```

Leave this process running throughout the test. With one USB connection, the monitor captures one card; observe the second card's screen locally. If both cards are connected through a shared hub, start the first card, wait until it is stable, then connect/start the second card. Do not repeatedly unplug or reset cards during the 38-second capture.

### 12.3 Capture operation

1. Start card A and confirm it reaches STATUS without reboot, white screen, or exit.
2. Start card B and place both cards at the measured distance. Wait until the peer/link state is stable.
3. On either card, use the current UP double-click action from STATUS to open DEBUG.
4. Use UP/DOWN click to select the preset target label matching the measured distance.
5. Press OK once. The screen must enter `COUNTDOWN`, then `SETTLE`, then `CAPTURE`.
6. Do not press buttons or move either card during the 3 s countdown, 5 s settle period, and 30 s capture period.
7. Wait approximately 38 seconds until the page shows `SUMMARY`, `RECORDS`, and `SAVED CSV`.
8. Preserve the USB log. The log should contain `CAPTURE_START`, `CAPTURE_META`, one stable `CAPTURE_CSV` header, CSV rows, and `CAPTURE_SAVE OK`.
9. After recording the result, return with OK. If needed, enter DEBUG again and use DOWN long-press to re-export the saved Flash record; this does not erase it.

### 12.4 Capture acceptance

Record the following without manually editing the raw log:

```text
firmware version
image SHA-256
measured distance and selected TARGET label
capture_id
boot_sequence
reset_reason
record count
CRC32
CAPTURE_SAVE result
whether the screen reached SAVED CSV
whether either card rebooted, went white, exited, or hung
```

A basic Capture PASS requires: one complete 38-second run; no reboot, panic, white screen, exit, or hang; a nonzero record count; `CAPTURE_SAVE OK`; matching `CAPTURE_META` and CRC32; and the expected CSV header/rows in `/tmp/pass-radar-usb-monitor.log`. This proves the capture/storage/export path, not distance accuracy. Do not tune FTM, RSSI, BLE, P25, or direction parameters from one run.

If the run is aborted, the page shows `INVALID`, the save result is absent, the CRC cannot be matched, or the monitor misses the save lines, record `FAIL` and preserve the complete log. Do not repeat parameter collection until the evidence is understood.

## 13. Stop conditions and next step

Stop parameter collection after any reboot, panic, white screen, exit, hang, unexplained FTM success, abnormal power condition, or missing raw evidence.

Next order:

1. Validate the Capture MVP on hardware at one measured distance;
2. Confirm the USB CSV header, row count, CRC/save status, and no reboot during the 38-second run;
3. Add token/obstruction/channel fields and an explicit, confirmed erase control;
4. Repeat across the controlled distance matrix;
5. Only then tune FTM, RSSI, sweep, and obstruction parameters.
